## Specialized Renderer Findings

`stage.greenfield.scaffold-plan` and `stage.greenfield.scaffold-implementation` are rendered exclusively by `src/greenfield/scaffold/renderScaffoldPrompt.ts`, NOT by the generalized `stageInstructionText` packet path used by the other 11 stages:

- `renderScaffoldPlanPrompt(ctx: GreenfieldPromptContext)` builds its entire output from a hardcoded template string plus `header(ctx)`; it never reads `ctx.stageInstructionText` (the type has no such field). It contains its own internal-path reference: `Use the bootstrap bundle's scaffoldPlanningInputs (src/greenfield/bootstrap/bootstrapBundleTypes.ts) as the source of truth` (line 56), and a bare implementation-symbol reference without a path: `matching the selected profile's target expectations (used by validateGreenfieldScaffoldPlan() for required-target and path-safety checks; ...)` (line 43).
- `renderScaffoldImplementationPrompt(ctx)` is likewise fully self-contained; its only path-shaped text is an illustrative target-project example (`e.g. "- src/cli.ts"`), which is a LEGITIMATE_TARGET_PROJECT_REFERENCE, not an Orchestrator-internal reference.
- Consequence: the `stage.greenfield.scaffold-plan` entry in `stageInstructionContent.ts` (containing its own, textually similar `bootstrapBundleTypes.ts` reference) is computed by `assembleStageContextBundleOrThrow` on every scaffold-plan prompt generation call but is discarded/unused -- it never reaches the coding agent. It is classified `MAINTAINER_REFERENCE_NOT_EMITTED_TO_AGENT` for that reason, while the textually similar reference actually inside `renderScaffoldPrompt.ts` is the real `CONFIRMED_INTERNAL_SOURCE_LEAK` for this stage.
- The `stage.greenfield.scaffold-implementation` catalog entry contains no `src/...` references at all and is also unused/dead for this stage (same bypass mechanism) -- moot for leakage purposes either way.
