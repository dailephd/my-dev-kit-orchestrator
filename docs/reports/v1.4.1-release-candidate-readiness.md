### Test-literal correction (explicitly authorized exception)

The initial `npm test -- --runInBand` run on the version-bumped release
branch returned 6 failed / 2928 passed, because six test files and one
generator-owned fixture hardcode the literal string `1.4.0` as "the current
release version" instead of deriving it from `package.json` or the
compatibility manifest:

- `tests/documentationConsistency.test.ts` (a documentation-preservation
  mutation embedded the pre-bump README version literal, making the mutation
  a no-op after the README was updated to `1.4.1`)
- `tests/v121Batch1Compatibility.test.ts`
- `tests/v121Batch3Compatibility.test.ts`
- `tests/v121CliRegression.test.ts`
- `tests/v121CompatibilityManifest.test.ts`
- `tests/v121PackageRegression.test.ts`
- `tests/compatibilityManifestLib.ts` (hardcoded `currentPackageVersion` field
  feeding the generated compatibility-manifest fixture)

Each was corrected with a pure `1.4.0` -> `1.4.1` literal swap (no assertion
weakened, no negative control removed, no behavior changed). The
`tests/fixtures/v121-compatibility/compatibility-manifest.json` fixture was
regenerated using the repository's own documented generator
(`GENERATE_COMPATIBILITY_MANIFEST=1 npx jest
tests/generateCompatibilityManifest.generate.test.ts --runInBand`), which
changed exactly the `currentPackageVersion` line.

This is a test-file change, which the standard release-scope rule (no
production/test file changes during release preparation) would ordinarily
block. The user explicitly authorized these exact 7 files as a narrow,
one-time exception: legitimate release maintenance to keep
version-preservation tests meaningful, not a design or behavior change, and
not a broader scope expansion. No other production or test file was changed.
After the correction, `npm test -- --runInBand` returns 0 failed, 11 skipped,
2934 passed.
