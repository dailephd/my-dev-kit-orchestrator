Exact wording changes made (all in the "stale stop condition" category -- each previously implied Android/mobile is categorically forbidden, which became false once android-compose shipped in Batch 2):
1. greenfieldIdeaBriefPrompt (promptGenerator.ts): "do not choose Android/mobile defaults" -> "do not silently choose a mobile/Android profile as a default when the request is ambiguous (see src/greenfield/profiles/resolveGreenfieldProfile.ts)". This preserves the real, still-true invariant (the resolver's fallback path never silently picks android-compose; ambiguous "mobile" text returns 'unresolved', per Batch 2) without implying Android is forbidden.
2. greenfieldStackDecisionPrompt: "Do not default to an unsupported (e.g. Android/mobile) stack." -> "Do not silently default to a mobile/Android stack when the request is ambiguous; only choose it when explicitly requested." Same reasoning.
3. greenfieldStarterProfilePrompt: "Supported profiles in v1.1.0: typescript-cli, nextjs-app." -> "Supported profiles in v1.2.0: typescript-cli, nextjs-app, android-compose." (factual correction) and "do not use Android/mobile profiles" -> "do not silently substitute a mobile/Android profile for an ambiguous or unsupported request".
4. greenfieldProjectDocsPrompt: "do not claim Android/mobile support" -> "do not claim Android/mobile support unless the selected profile is android-compose (see src/greenfield/bootstrap/validateBootstrapDocs.ts)" -- this now correctly matches Batch 3's profile-conditional validateBootstrapDocs() behavior instead of contradicting it.
5. renderScaffoldPlanPrompt: "do not add Android/mobile file trees or profiles" -> "do not add file trees for a profile other than the one selected in the bootstrap bundle" -- generalized to name the real invariant (don't invent scope beyond the selected profile) rather than hardcoding "Android" as the forbidden case, which is also more correct if a future profile is ever added.
6. renderScaffoldImplementationPrompt: "do not add Android/mobile behavior" -> "do not add behavior for a profile other than the one selected in the bootstrap bundle" -- same reasoning.

These are the only production changes made in this batch. All six are wording-only corrections to static prompt text; no runtime logic, data structures, or control flow changed. None are Android-specific branches -- five of the six are reworded to reference "the selected profile" generically (matching section 7.6's preference for a generic profile-aware alternative over an Android-specific carve-out); only the two purely factual corrections (profile count/names in greenfieldStarterProfilePrompt) name android-compose explicitly, because they are stating a catalog fact, not a rule.
