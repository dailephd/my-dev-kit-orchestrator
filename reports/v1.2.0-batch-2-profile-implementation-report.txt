PROFILE RESOLUTION
- aliases added (explicit, bounded, no fuzzy matching): `android`, `kotlin-compose`, `jetpack-compose`, `compose-android` (all normalized-form keys). Spaced variants ("android compose", "kotlin compose", "jetpack compose") are not separate alias entries -- they already normalize to their exact catalog/alias key via the pre-existing lowercase+dash-join step every profile request already goes through, so no duplicate alias entries were needed for them.
- generic mobile ambiguity behavior: a request of exactly `mobile`, `mobile-app` (from "mobile app"), or `phone-app` (from "phone app") as an explicit `preferredProfile` value, or a `platformTarget`/`preferredStack` signal matching `/\b(mobile|phone app|phone-app)\b/i` with no `preferredProfile` at all, returns `status: 'unresolved'` (the pre-existing, previously-unused status value) with a reason naming android-compose as available-but-must-be-explicit and iOS/Flutter/React Native as unsupported. Deliberately narrow: does not match "android", "kotlin", or "compose" alone (those are handled by the alias table above, not this ambiguity path), and does not extend fallback (non-explicit) resolution to auto-select android-compose from a bare "android" signal in platformTarget/preferredStack the way the existing WEB_HINT_RE auto-selects nextjs-app from "web"/"react" signals -- this was a deliberate scope decision (see "Deferred items" below), not an oversight.
- unsupported platform behavior: iOS, Flutter, and React Native (and their spaced/dashed variants) are not added to `SUPPORTED_PROFILES` or `PROFILE_ALIASES`, so they continue to fall through the pre-existing catalog-miss branch producing `status: 'unsupported'`, unchanged from v1.1.0.
- no fuzzy matching confirmation: `PROFILE_ALIASES` and `AMBIGUOUS_MOBILE_PROFILE_IDS` are both plain object/Set exact-key lookups against the already-normalized request string; no regex-based partial matching is used for alias resolution (the `MOBILE_HINT_RE`/`WEB_HINT_RE` regexes are used only for the fallback path's free-text signal detection, which is a pre-existing pattern from v1.1.0, not new fuzzy-alias behavior). Regression-tested: `androidx`, `androidish`, `kotlin` (alone), `compose` (alone) do not resolve to android-compose.
