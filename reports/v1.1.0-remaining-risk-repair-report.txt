EXPORT TRAVERSAL FIX

Root cause: `isSafePath()` in src/commands/export.ts was called with the already-`path.resolve()`d output path (`isSafePath(outPath)` where `outPath = path.resolve(options.out)`). `path.resolve()` normalizes away `..` segments before the function's own `outputPath.includes('..')` check ever runs, so the check could never fire for any traversal attempt, on any mode, on any platform.

Files changed:
- src/commands/export.ts -- `isSafePath()` now takes two parameters: `rawInput` (the raw, pre-resolution `--out` string) and `resolved` (the resolved absolute path). The `..`-substring check now runs against `rawInput` first; the existing directory/symlink checks continue to run against `resolved`, unchanged. The call site now passes `isSafePath(options.out, outPath)` instead of `isSafePath(outPath)`.
- scripts/cli-smoke.mjs -- unrelated to the traversal fix itself, but fixed in the same pass after being discovered broken (see "Not changed" section for why it was in scope): `smokeHelp()` hardcoded an expectation of CLI version "1.0.0", which fails now that package.json is at 1.1.0. Replaced with a dynamic read of package.json's own version. Also added a new `smokeGreenfield()` category (init, start --mode greenfield, prompt, status, list, check --artifacts, check --all, export), wired into the mode dispatcher and into .github/workflows/validate.yml, since section 6.6 requires greenfield smoke coverage in CI.

Behavior before: `export --out ../x.txt` succeeded (exit 0) and wrote a file one directory above the current working directory, for every mode.

Behavior after: `export --out ../x.txt`, `export --out ..\x.txt`, `export --out nested/../../x.txt`, and `export --out nested\..\..\x.txt` are all rejected (exit 1, "output path contains path traversal (..)"), for every mode, on this platform (Windows). Safe relative paths (`export.txt`, `./export.txt`, `reports/export.txt` into an existing subdirectory) continue to work exactly as before. The pre-existing, already-working safety checks (reject existing directory, reject symlink) are unchanged and continue to pass.

Cross-platform path handling: the fix is a plain substring check (`rawInput.includes('..')`) against the raw CLI argument, before any path parsing occurs. This works identically regardless of which separator convention the raw string uses (`/` or `\`), since no path-specific parsing is involved in the detection itself -- confirmed by testing both `../x.txt` and `..\x.txt` styles locally (this platform is Windows, where both separator styles are meaningful to the OS; on macOS/Linux, a raw `..\x.txt` argument is not treated as a directory reference by the OS itself, but the raw-substring check still correctly flags it as containing a suspicious ".." sequence, which is the intended conservative behavior -- reject when uncertain, per the pre-existing design intent already documented in the function's own comment).

Tests added: src/__tests__/run-export.test.ts, new describe block "export --out path traversal rejection (CLI-level regression)" -- 12 new tests covering: unix-style relative traversal, windows-style relative traversal, nested unix-style traversal, nested windows-style traversal (all for feature mode), traversal rejection for greenfield mode, traversal rejection for repair mode (non-regression check), a safe relative path (chdir'd into the run directory, since `--out` resolves against process.cwd() like any CLI tool, not against `--root`), a safe nested relative path into an existing subdirectory, a safe `./`-prefixed relative path, and confirmation that the pre-existing existing-directory rejection still works unaffected by the fix.
