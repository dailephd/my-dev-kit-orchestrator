VALIDATEBOOTSTRAPDOCS CHANGES
- profile-aware validation: `validateBootstrapDocs(result, selectedProfileId?)` -- the second parameter is optional, so all pre-existing call sites (which never passed a profile id) continue to compile and behave exactly as before (Android/Jetpack claims still flagged by default, i.e. when no profile id is passed or it is not `'android-compose'`).
- Android Compose allowed claims: `android`/`jetpack` mentions no longer produce an `android-mobile-claim` issue when `selectedProfileId === 'android-compose'`.
- non-Android rejected claims: unchanged behavior for every other profile id (or when omitted).
- release/security/publish rejected claims: unchanged, still always-on for every profile.
- new: Play Store/release-readiness claims (`play store`, `app release`, `release-ready`/`release ready`) are now their own always-on check (`play-store-release-readiness-claim`), separate from the general release/security/publish check, since section 7.4 called this out as its own explicit requirement ("Play Store/release-readiness claims must be rejected for Android Compose unless explicitly framed as future/non-goal limitations" -- Batch 3 rejects them unconditionally rather than trying to detect "future/non-goal framing," which would require natural-language understanding beyond a regex; this is documented as a conservative, deliberate simplification, not an oversight).
- unsupported platform claims (iOS/react-native/flutter/kotlin-multiplatform/compose-multiplatform): split into their own always-on, profile-independent check (`unsupported-platform-claim`), separate from the Android/Jetpack conditional check, since these must never be permitted for any profile including android-compose.

SCAFFOLD PLANNING CHANGES
- setupCommands integration: `buildScaffoldPlan()` now reads `profile.setupCommands` directly. For android-compose this is `[]` (no separate install step); for typescript-cli/nextjs-app it is `[{ command: 'npm install', ... }]`, identical to the previous hardcoded behavior.
- validationCommands integration: `buildScaffoldPlan()` now reads `profile.validationCommands` directly. For android-compose this is the three Gradle commands (build/testDebugUnitTest/connectedAndroidTest, the last marked `required: false` with a device/emulator note); for typescript-cli/nextjs-app it is the same three npm commands as before, now carried as `GreenfieldProfileCommand` objects instead of plain strings.
- hardcoded npm assumption removed or constrained: the `buildValidationCommands()` keyword-sniffing helper (which mapped `profile.validationExpectations` substrings like "typecheck"/"build"/"test" to hardcoded `npm run ...` strings) was removed entirely as dead code; `setupCommands`/`validationCommands` are no longer derived by inference from `validationExpectations` prose at all -- they are sourced from the profile's own dedicated command fields, which is a strictly more correct design (no more risk of a future profile's prose accidentally matching an npm-shaped keyword).
- TypeScript CLI regression behavior: preserved exactly; only the data *shape* changed (object instead of string), not the command values or count.
- Next.js regression behavior: same.
- Android Compose command behavior: setupCommands empty; validationCommands are the three Gradle commands; entry-point detection now recognizes `.kt` files (broadened regex), confirmed to still correctly detect `.ts`/`.tsx` for the other two profiles (regression-tested).
