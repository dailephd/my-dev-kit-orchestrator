Artifact: V120DocumentationCompatibilityPlan
Batch: v1.2.0 Batch 1

PURPOSE
Define a hardened documentation workflow for v1.2.0 so every user-facing document is accurate after implementation, and so the docs:check gate that v1.1.0 introduced does not silently go stale the way it would have if this plan were skipped (the profile-list regex and Android-claim patterns in scripts/check-docs-consistency.mjs are, as written today, guaranteed to either fail incorrectly or pass incorrectly once Android Compose ships -- see architecture audit).

DOCUMENTATION HARDENING REQUIREMENT
- Documentation updates in Batch 5 must not be a vague "docs cleanup." Every claim added or changed must trace to a specific, verifiable source: source code, package.json, CLI output, or a passing test.
- Every user-facing doc listed below must be audited, not just the ones an author assumes need changes.
- Every stale claim found must be listed explicitly (doc, line/section, claim, correction) before being fixed, not fixed silently.
- scripts/check-docs-consistency.mjs must be updated in the same batch as the doc content it protects, never after.
- Documentation is not complete until `npm run docs:check` and `npm run lint:docs` both pass, and the full test suite (including src/__tests__/docs-consistency.test.ts) passes.

SOURCE-OF-TRUTH EXTRACTION (what Batch 5 must read before writing a single doc sentence)
- package.json: name, version, scripts, bin (confirms exact version string and command names to reference)
- CLI help (`node dist/cli.js --help` and each subcommand's `--help`): confirms exact flag names/wording
- src/types.ts: VALID_MODES (confirms the mode list/count; Android Compose does not change this, so mode-count claims should not change)
- src/workflows.ts / src/greenfield/modes/greenfieldStages.ts: confirms the 13-stage list is unchanged
- src/greenfield/profiles/*.ts (profileTypes.ts's `GreenfieldProfileId` union, and `resolveGreenfieldProfile.ts`'s `SUPPORTED_PROFILES` keys): the actual, ground-truth list of supported profiles -- this is the exact list docs must mention, extracted programmatically by docs:check rather than hand-copied
- src/greenfield/bootstrap/buildBootstrapBundle.ts's `buildValidationRules()`: confirms the exact validation-rule id/description strings if docs ever quote them
- src/greenfield/scaffold/*: confirms scaffold-plan content categories (file groups, setup/validation commands) if docs describe scaffold planning in more than a sentence
- tests (tests/greenfield/*.spec.ts, src/__tests__/docs-consistency.test.ts): confirms which behaviors are actually regression-tested, so docs do not claim more than what's tested
- CI (.github/workflows/validate.yml): confirms the actual Node/OS matrix and step list, if docs describe CI coverage
- security script (scripts/test-security.mjs): confirms what the security contract check actually validates, if docs describe it

REQUIRED STALE-CLAIM SEARCHES (Batch 5 must run these, not just trust this plan's predictions)
- "Android planned" / "planned Android" / "Android Compose planned" / "planned Android Compose"
- "mobile planned" / "planned mobile"
- "no Android support" / "does not support Android" / "does not implement Android"
- "v1.2.0 planned" (once v1.2.0 ships, this becomes stale the same way "v1.1.0 planned" was)
- "v1.1.0 current" / claims that v1.1.0 is the current/latest version (v1.2.0 supersedes it)
- stale profile list: any doc still saying only `typescript-cli` and `nextjs-app` are supported, without `android-compose`
- stale package version: any doc referencing `@1.1.0` or an older version instead of the actual shipped v1.2.0 version
- stale mode list: not expected to change (Android Compose adds no mode), but re-verify no doc miscounts modes as a side effect of an unrelated edit
- stale artifact paths: not expected to change (no new artifact paths), but re-verify docs/ARTIFACTS.md's greenfield table still matches `GREENFIELD_ARTIFACT_MAP` exactly
- unsupported Flutter/React Native/iOS claims: docs must continue to explicitly state these are NOT supported (this is a claim that must be added/kept, not removed, once Android Compose makes "mobile" support partially true)

DOCS:CHECK REQUIREMENTS (scripts/check-docs-consistency.mjs changes required in Batch 5)
- Android Compose current-support check: add an assertion (or extend the existing per-mode-token loop's pattern) that `android-compose` is mentioned in docs/WORKFLOWS.md and/or README.md as a current, supported profile.
- unsupported platform claim check: keep (or add, if not already present in this exact form) an explicit check that docs state React Native/Flutter/iOS are NOT supported -- this is a new, positive requirement (the opposite of the current `misleadingAndroidClaims` pattern, which only rejected premature claims; Batch 5 needs both "must claim android-compose support" and "must not claim RN/Flutter/iOS support").
- profile list consistency: **refactor**, do not just extend, the current hardcoded regex at line ~125 (`/supports the\s+\`typescript-cli\`\s+and\s+\`nextjs-app\`\s+profiles/i`). Add an `extractGreenfieldProfileIds(root)` function that reads `SUPPORTED_PROFILES`' keys from `src/greenfield/profiles/resolveGreenfieldProfile.ts` (or the `GreenfieldProfileId` union from `profileTypes.ts`), mirroring the existing `extractModes()`/`extractGreenfieldStages()` pattern exactly, then assert every extracted profile id appears in docs/WORKFLOWS.md (and/or README.md). This makes the check self-updating for any future profile (v1.3.0+) instead of requiring a hand-edit of a hardcoded regex every time.
- artifact docs consistency: no change expected (see "Required stale-claim searches" above), but re-run as regression.
- package version reference consistency: no change expected; the existing `!readme.includes(pkg.version)` check already generalizes to whatever version is in package.json at Batch 5 time.
- roadmap/changelog historical exception handling: the existing pattern already treats older version sections (v1.0.0, v0.6.0, etc.) as historical and does not re-validate their content -- Batch 5 must preserve this exception (do not make docs:check retroactively validate historical changelog/roadmap entries) and only add new v1.2.0-scoped checks, following the same "current version's claims only" pattern already established for v1.1.0.
- **Narrow the `misleadingAndroidClaims` patterns** (currently `/supports android/i` and `/supports mobile/i`, unconditionally rejected): once docs correctly say "supports Android Compose," these two patterns will produce false-positive failures forever. Replace them with patterns that remain meaningful post-v1.2.0, e.g.:
  - keep version-scoped patterns exactly as-is (`/v1\.1\.0.{0,80}android profile/i`, `/v1\.1\.0.{0,80}mobile profile/i`) -- these describe a specific historical claim about v1.1.0 that must never appear, and remain valid forever since v1.1.0's scope is now fixed history.
  - drop the bare `/supports android/i` and `/supports mobile/i` patterns (or narrow them to something like `/supports android(?!\s+compose)/i` if a residual guard against overclaiming general Android support -- as opposed to specifically the Compose starter profile -- is still wanted).
  - add narrow, permanent patterns for what must never be claimed regardless of version: `/supports react.?native/i`, `/supports flutter/i`, `/supports ios/i`.
